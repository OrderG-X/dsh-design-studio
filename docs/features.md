# Design Studio: all features

The repo front page shows only the highlights. This page lists every feature, the tool parameters and the security design. For install and quick start, see the [front page](../README.en.md).

## Finding things (1.0)

Every control in the sidebar lives in one of these places:

- **Title bar** (the top row): the logo goes home; the project name ▾ is **Page setup** (type, size, sizes side by side, fit to size, dark mode, refresh, open in browser, Open HTML…); the grid goes back to the canvas and the screen name ▾ switches screens (with a search box when there are many; ↑↓ to pick, Enter to view alone); on the right are **Share**, **Export** and **Build as code**. On the home page the middle holds four tabs, Home / Gallery / My designs / Inspiration, and the right side says Back to "project".
- **Island** (the bar at the bottom): **Ask or run a command** | Select, Text, Style, Annotate | Present, Theme, Check (with the problem count). In a mode, the whole bar turns into that mode's controls and turns back when you leave: the model at work (screen, lines written, time, Stop), Present, an old version, Visual diff, and Annotate. **Versions** sits at the bottom left and zoom (zoom in, zoom out, fit, actual size) at the bottom right.
- **Panels** (one at a time): Theme (Global styles / Tweaks / Restyle / Brand), Check, Style, Versions, Export, Share (Phone preview / Online link / HTML demo / Submit to gallery) and Build as code. Under 1000 px wide a panel is a drawer that rises above the island while the canvas makes room; with DSH full screen (1000 px and up) it is a card on the right. Text, Annotate, Present and Visual diff don't open a panel; they only change the island.
- **Command palette**: click the left end of the island, or press ⇧⌘K (Ctrl+Shift+K on Windows). The DSH desktop app uses ⌘K for searching sessions, so the studio leaves it alone; the key is registered in DSH Settings → Shortcuts, where you can change it. Type a few letters to find a command (jump to a screen, export a PDF, check, phone preview, home…) and press Enter to run the first one; ⇧Enter sends what you typed to the model as a message.
- **Single keys** (when the canvas has focus): V Select, T Text, S Style, P Annotate, R Present, L Theme, C Check. The hover cards list them.

The words mean one thing everywhere: **Save** writes straight to the files without the model (a version is kept before and after); **Ask the model** hands it to the model and sends right away; **Add to chat** only puts it in the input so you can add a sentence first.

When something breaks: if a screen won't open (the file is gone, the dev server stopped), it gets a red outline and a "Won't open" tag, with a card naming the file or port plus **Retry** and **Ask the model**; the card goes away by itself once the file is back. Toasts for things that failed (export, open, restore a version…) carry **Retry**.

On a narrow sidebar (under 440 px) the title bar keeps only icons, the island keeps only icons (the input becomes a sparkle), Versions and zoom move to a row above the island, and panels lay out in one column.

## What it does

1. **Opens by itself, but only for design work.** Design work means the model loaded the design skill, called `preview_page`, or wrote a page with a design-type tag (`<meta name="dsh-design">`). After that, the tab pops up when the model writes an `.html` file or starts a dev server (`npm run dev` and the like). HTML written by other tasks doesn't pop up. Instead, a blue dot appears on the header button, and clicking it previews the file. Ports the model only probes with `curl` or the browser tools are never opened.
2. **Frames by design type.** Supported types are web (browser window), app (phone with Dynamic Island), miniprogram (a WeChat mini program: the phone frame plus WeChat's top-right capsule, which turns white over a dark top bar; a page can force it with `<meta name="dsh-capsule" content="white">`), desktop (a 1280×800 app window with macOS traffic lights at the top left; `<meta name="dsh-design" content="desktop windows">` draws the Windows buttons at the top right instead, white over a dark top bar), tablet, poster (1080×1350), slides (16:9), email and diagram (mind maps, technical route charts, product roadmaps and architecture diagrams; 1600×1000 by default with no device frame, growing with the diagram when it is larger). The model names the type in the tool call, or the page declares it with `<meta name="dsh-design" content="app">`. You can add a size, as in `poster 1080x1920`. Type in Page setup (the project name ▾) switches it at any time. Slides and posters larger than the default size now use the page's real size. You can also set it by adding `WIDTHxHEIGHT` after the type, for example `<meta name="dsh-design" content="slides 1440x810">`.
3. **Shows several screens on one canvas.** HTML files in the same folder line up in creation order. Pan with two fingers and zoom with a pinch or ⌘ + scroll. Zoom options sit under the zoom menu at the bottom right. Click a screen to select it and double-click to view it alone; single view has ‹ › for the previous and next screen, with the neighbors peeking in at the sides. With many screens, only the 24 nearest the view are live pages (to save graphics memory); the rest show a thumbnail the plugin takes in the background (refreshed when the file changes) and turn into the live page when you move closer.
4. **Lets you watch it build.** A placeholder appears while the model works. The screen being built gets an aurora ring with a glow behind it, the island shrinks to a status capsule (which screen, how many lines, how long, and Stop when DSH allows it), and a finished screen flashes once. Each new screen fades in from top to bottom with a scan line. While more screens are coming, a "generating…" card waits at the end of the canvas. When the model asks you something with a question card, the status turns into an orange dot reading "The model is waiting for your answer".
5. **Refreshes live without a white flash.** The next frame loads in the background and cross-fades in, keeping the scroll position. Dev servers keep their own hot reload; Vite and Next WebSockets pass through, including dev servers that only listen on IPv6 `::1` (recent Vite on macOS).
6. **Highlights what changed.** Changed and new elements glow briefly, and the preview scrolls to them if they are off screen. Shared CSS changes refresh every screen. A change to one screen's HTML leaves the others alone.
7. **Picks elements for the chat.** Hover outlines elements with their size. Click picks one element. Drag picks a region along with up to 10 main elements in it. On DSH 0.2.1+ the pick becomes a small chip in the chat input labeled "1 element" (a region shows how many elements it holds). Hover it, in the input or in a sent message, for the element, selector, size and file. When you send, the model gets the full block: the file, the CSS path, the HTML and key styles. Older DSH inserts that block as text, with the caret on a new line below it. Everything else the studio puts in the input also lands as a chip on DSH 0.2.1+, each with its own icon: annotated images, text edits, style changes, more takes, a picked direction, the check list, build as code, reference images, tweaks, design systems, style cards and design tokens. Hover shows the gist (annotated and reference images show a thumbnail); the model still gets the full text.
8. **Ships a built-in design guide.** The DSH skill `ui-design` loads before the model designs. It sets the type and size, writes `tokens.css` first and uses one file per screen. It covers spacing, type scale, color, contrast, Chinese typography, an "AI-look" blacklist and a self-check list, with notes for each design type. For a brand-new design the model first asks two or three key questions, then lays out three directions for the first screen (`home-a/b/c.html`, each with its own colors and fonts) side by side; you pick one and it builds the rest, moving the others to `drafts/`. If you already chose a feel in the questions, the three directions all stay in that feel and differ in layout and emphasis. Say "just build it", or give a specific brief, to skip this.
9. **Theme › Global styles.** The first tab of Theme on the island (or L) lists the `:root` variables grouped by color, font, size, spacing, radius and shadow, with swatches. Click one to put it in the chat, say "make it forest green", and every screen updates together.
10. **Exports.** **Export** in the title bar opens the export panel, as does **Export** next to a selected screen's label. Pick the format (image, PDF or PowerPoint) and which screens (all, just this one, or a few); image styles are with device frame, without device frame, full page and showcase. You can export one screen with its device frame or plain, a full-page capture, or a **showcase** of all screens. The showcase uses the brand name as its title and takes its background and accent from your tokens. You can also export every screen as a **PDF** (one page per screen; web and email pages are full length, and page size follows the design's size) or a **PowerPoint** file (one slide per screen as an image, with the slide shape following the design's size; opens in PowerPoint, WPS and Keynote). Links between screens still work: in the PDF a button jumps to its page (and every screen has a bookmark), and in a slideshow it jumps to its slide, so the export is a clickable prototype. Files go to `exports/` in the design folder, and images are also copied to the clipboard. Export options let you pick the page size (16:9, 4:3, A3 landscape or custom), the capture (current viewport, full-length page or a set height) and two screens per page. If anything would be cut off, you get a checklist first, with a one-click fix that fits the size to the content. **HTML demo** (Share › HTML demo; designs from local files): every screen goes into one `.html` file with its styles, images and icons inside, so a client or manager can open it with a double-click in any browser. It has the phone, tablet or browser frame (switch it off with "Device frame" at the top), buttons and links change screens, ← → flip through them, and it can go full screen; a phone design opened on a phone fills the screen. Screens, version, size, light or dark, and tweak values match the sidebar at the moment you export. No AI is involved, so it takes seconds. **Online link (beta)** (Share › Online link) puts that demo online for a while: you get a link and a QR code, and the other person can open it in WeChat or any browser without being on your Wi-Fi, and click through the screens. It uses a free Cloudflare quick tunnel (trycloudflare.com; it needs cloudflared, which the panel can download for you). Only this demo is reachable, nothing else on your computer. The link has a random key, closes after 2 hours or whenever you click Stop sharing, and stops working right away. Edits show up when they refresh; switching to another design closes it. When a design has more than 60 screens the sidebar shows only the newest 60, but PDF, PowerPoint, the HTML demo and the online link still include the hidden ones (in the order they were made, up to 1000 screens per export, with "Capturing 120/400…" progress); the showcase uses only the screens in the sidebar.
11. **Keeps versions.** A version is saved before and after every model turn, named after what you asked (a picked element becomes a short name such as “「3.2 km」 · make it green”, not a selector dump). **Versions** at the bottom left opens a row of version cards. Open any version and the island becomes "version · time | Compare with now | Restore | ×": drag the slider to compare it with now, or restore it. The current state is saved first, so restoring is always reversible.
12. **Switches to dark mode.** If the page has dark styles (`prefers-color-scheme: dark`, `[data-theme="dark"]` or `.dark`), Page setup gets a **Dark mode** item that toggles them, and exports follow.
13. **Makes two more versions.** Select a screen and ask for two alternative directions. They appear right next to the original on the canvas (the three starting directions `home-a/b/c` too, kept in a, b, c order). Click **✓ Use this take** next to the title of the one you want (it shows on every take, no need to select it first): the chat input gets "use this one, move the other takes to `drafts/`, build the rest", ready to send.
14. **Phone preview.** Share › Phone preview shows a QR code. Scan it with a phone on the same Wi-Fi and the design opens in the phone's browser at real size, fully tappable. The phone follows the screen you pick on the computer and refreshes when the model changes the design. The panel shows when the phone has opened it, lets you copy the link and Stop sharing, and closes the link after 30 minutes idle. While it is on, the Share button has a green dot.
15. **Works as a clickable prototype.** Screens link to each other with `<a href="detail.html">` or `data-href` (the built-in skill asks the model to do this). Select a screen on the canvas to see where it leads: each line starts at the button, runs through the gaps between screens with rounded corners, keeps its own lane and avoids crossings, and never cuts through another screen. Navigation that every screen has (tab bar, back) just gets a dashed outline instead of a line. **Present** on the island (or R) starts presenting: tap a button in the preview and the linked screen slides in, from the right going forward and from the left going back. The island becomes "Presenting · screen | Back | Restart | ×", and Esc also leaves. Write a back arrow as `<a href="home.html" data-back>`: when presenting, in phone preview and in the HTML demo it returns to the previous screen (wherever you came from), and goes to `href` only when there is none.
    **Page states** (#30): the different looks of one page (empty list, with data, paid, error) live in one file instead of extra screens. Declare them in `<head>` with `<meta name="dsh-states" content="default:With data, empty:Empty list">` (the first is the default, up to 8), write the differences as CSS on `[data-state="empty"] …`, and link to a state with `order.html?state=paid`. A state button appears next to the screen name on the canvas: switch states there or show all states side by side; in single view it sits in the title bar. Presenting, phone preview and the HTML demo follow state links; the design check measures every state; Export can make one image per state; and the code handoff describes the page as one component with states.
    **Mock data** (#30): for a prototype whose clicks really change things and survive page changes, the model writes `mock.json` (a JSON object) in the design folder as the data source and binds the pages to it with `data-mock-text` (show a value), `data-mock-show` (show if), `data-mock-each` (lists), `data-mock-set` (change data on click), `data-mock-model` (two-way inputs), `data-mock-class` / `data-mock-attr` and `data-mock-reset` (a reset button). States can follow the data too (`<meta name="dsh-states" … data-mock="user.stage">`), so a global stage such as interviewing / on site changes every page at once. Changed data is kept in the browser across page changes and reloads; with several screens open on the canvas, a click in one updates the others at once; editing `mock.json` starts over from the new file. The island gains **Data** (only when there is a `mock.json`): the data as a tree, changed values marked with an orange dot; edit text and numbers in place, flip switches, add or delete list items; **Reset** goes back to `mock.json`, and **Save as initial data** writes the current data into `mock.json` (as a new version you can roll back). The design check, screenshots and thumbnails use the initial data whatever you clicked, and the check reports broken expressions and fields missing from `mock.json`. The HTML demo carries the data (stored once) and the player gains a Reset data button; the code handoff says to build it as initial data plus global state and lists the fields each screen uses.
16. **Shows one screen at several sizes.** Page setup › Sizes lays the current screen out at several widths: phone, tablet and desktop for web; small, standard and large for apps; three sizes for tablets. Cramped small screens show at a glance. Picking works there too and notes the width.
17. **Edits text in place.** Turn on **Text** on the island (or T) and click any text in the preview to edit it. Enter saves and Esc cancels. Local HTML is written back to the source file, only that one spot, with a version saved before and after. For dev-server pages, or when the text isn't in the source, a "change X to Y" request goes into the chat input for the model.
18. **Takes a reference image.** Drop an image onto the sidebar, paste it there, click Reference image on the Home page, Reference… in Theme › Restyle, or Use as reference on an image in Inspiration. The image is saved to `refs/` in the design folder (or the plugin cache when there is none). Its main colors with their shares, any small vivid accent, and whether it reads light or dark go into the chat input with the file path and an instruction to update `tokens.css` first.
19. **Checks the design.** **Check** on the island (or C) measures the rendered pages: text running off the screen, clipped, overflowing its box or overlapping; text contrast below WCAG (3:1 for large text, 4.5:1 for body); tap targets below 44 px in apps or 24 px on the web; tiny text; images that failed to load or are stretched; lines that are too long on web, email and tablet (about 45 Chinese characters or 90 letters); short labels and prices squeezed onto two lines; too many font sizes; text or buttons under the mini program capsule, the Dynamic Island or the phone's home-indicator strip; more than 5 bottom tabs; a mini program page with no top navigation bar; and, in desktop apps, text or buttons under the window buttons. Every screen on the canvas is checked, and numbered markers appear on the problems in the preview (red for serious ones). Click an item to scroll to it. **Ask the model** sends the list (screen, element, problem, by how much) to the model. After every model turn the sidebar measures again by itself: an open panel refreshes, and a closed one shows the number of remaining problems on its button (no number means all clear). Clicking an item brings its screen into view when the panel covers it or it is off the canvas. The model can run the check itself: in Design mode it calls `check_design` after writing or changing screens. The plugin opens each screen at real sizes in a hidden Chrome or Edge on this computer (several sizes at once, such as a short 375×667 and a large 430×932, and dark mode if asked). Besides the same list, it reports each screen's measurements (page height, top and bottom bar heights and their gap to the content) and catches four more problems: fixed top or bottom bars covering content or sitting too close to it (like the last row hidden under a tab bar; content merely scrolling under a bar is fine), script errors, stylesheets, scripts or fonts that failed to load, and links to screens that don't exist. Low-contrast and tiny text also name the CSS rule that sets them, with file and line. Serious problems (covered by a bar, overlapping, clipped or overflowing text, running off the screen, broken images, very low contrast) come with a close-up screenshot of that spot (up to 4, taken at the size and scroll position where it was found: the element outlined in red with the amount on it, the other one of an overlapping pair in orange, a covering bar made see-through, nearby problems sharing one picture), so the model doesn't need a separate screenshot. Overlapping text also gets a likely cause (negative margin, absolute positioning or a transform) with the rule's file and line, and overlaps with the same cause are listed as one. A repeat run says how many problems were fixed and how many are new (new ones are marked), and an incomplete run says so. The sidebar doesn't need to be open; without Chrome or Edge the sidebar measures instead. When a shared part (the same class, such as a card or a button) is styled differently in different screens' own `<style>`, the panel shows a separate "Shared parts differ across screens" reminder (not counted as a problem; older designs can show it too; click one to put "make this part consistent" in the input), and the model's check result includes it so the model can move one version into the shared `app.css` (#30).
20. **Lets the model look.** When the model wants to see the real rendering it calls `look_design`. The same hidden browser takes a screenshot at a given size (the top, scrolled to the bottom, the whole page in parts, or one element such as the tab bar, in light or dark) and hands the image to the model. No servers or screenshot scripts of its own.
21. **Learns your brand.** Give the model a website or a project folder ("follow our site's style") and it calls `extract_design_system`. The hidden browser opens the site and measures what it actually renders: page and surface colors, body and secondary text, brand and accent colors, borders, fonts and the type scale, radii, shadows, and how the primary and secondary buttons, inputs, cards and header look. A project folder is also scanned for CSS variables, hard-coded colors, Tailwind config and component libraries. The result is a full set of files in `~/.dsh/design-systems/<brand>/`: `tokens.css` (same variable names as the skill's starter), `components.css` (buttons, inputs, cards, text styles), a `components.html` specimen and a `DESIGN.md`, plus screenshots of the site and its components. Once it is the default, every new design starts from it: the model skips the "what feel?" question and varies the three directions in layout only. Theme › Brand lists them (Brand… in the home ＋ menu opens the same place) with a specimen thumbnail and swatches, and lets you set or clear the default, apply one to the current design, or enter an address to extract a new one.
22. **Tweaks.** The model picks the dimensions most worth trying for this design (spacing, radius, brand color, card layout…) and writes them to `tweaks.json`. Theme › Tweaks shows them as sliders, color pickers and choices. Dragging updates every screen on the canvas at once (only CSS variables and `<html>` attributes on the live page; files are untouched). When you like it, **Save** puts variables into the defaults in `tokens.css` and attributes onto each screen's `<html>`, with a version saved before and after; "Ask the model" has it apply the values and adjust related details. With no tweaks yet, one click asks the model for some, and `check_design` also reports tweaks that aren't wired up.
23. **Builds it as code.** **Build as code** at the right end of the title bar asks what to build with (same as the existing project, React, Vue, Next.js or plain HTML; mini program designs also get uni-app and native WeChat, defaulting to uni-app), where to put the code and whether to do all screens or just this one, then "Start building". The model first calls `handoff_design`, which writes `handoff/HANDOFF.md` in the design folder (each screen's file, suggested route and links; the tokens; parts shared by several screens that should become components; scripts, forms and hover states; tweaks; images and fonts; steps and acceptance) plus top-to-bottom screenshots of every screen. It then builds one screen at a time, and after each one runs the dev server and calls `compare_design`: both pages are captured at the same size and compared pixel by pixel, returning a "design | actual page | difference" image with the worst areas boxed and numbered, which element each one is on both sides, and the overall difference. It moves on once that is under 3%. After a comparison the sidebar offers **Visual diff** (the Build as code panel also has a per-screen checklist: click a screen to compare it): the design and the actual page are shown together, and the island holds the address, Split (drag the line) / Overlay (opacity, Difference) / Side by side, the difference, Diff boxes and Compare again, scrolling together; for framed designs the actual page covers only the main area. The island shows the difference score (click it for the image), "Compare again" reruns at the current size, Diff boxes mark the differences, and if you click through to another page in the real app the island offers "Compare this page".
24. **Marks up the preview.** **Annotate** on the island (or P) lays a drawing layer over the preview, and the island grows to two rows (tools with undo / redo / clear; colors, sizes and Cancel / Copy / Add to chat). Draw right on the page with a pen, highlighter, arrow, rectangle, circle or text, and erase whole strokes with the eraser; pick from eight colors and three sizes, undo and redo (⌘Z / ⇧⌘Z) or clear everything. Hold Shift for squares, circles and 45° arrows. The first three times, a short how-to sits in the middle until you draw, and the bottom bar always says how the current tool works ("Circle · Drag to circle what needs changing"). Shapes, arrows and text come out hand-drawn, like marking up a printout with a pen. It works in single view and on the canvas, and the preview holds still while you draw. **Add to chat** captures every screen visible on the stage, lays them out where they sit, draws your markup on top, crops to the marked area and saves the image to `refs/` in the design folder (`markup-<screen>.png`). The chat input gets an "Annotate" chip (hover it to see the image and your notes); the model gets `[Markup]`, the image path, an instruction to look at it with `read_image` and change what the markup points at, and any text you wrote on it, so you only add what to change. **Copy** (⌘C) puts the same image on the clipboard to paste into another tool or chat (hidden when the studio is opened remotely over plain http, such as a LAN address, where browsers block clipboard writes). Esc or Cancel leaves without keeping the drawing.
25. **Opens HTML you already have.** Home ＋ › Open HTML… (also in Page setup) picks a local HTML file (the web version uses an address box with Browse and Open), or drop an HTML file or folder onto the sidebar to open it (desktop app; the web version can't see local paths, so type the path there). The address box takes a file path, a port or a localhost address. A folder opens its `index.html`, or else the first screen made, and the other screens in it still line up on the canvas. The brand design system source and the handoff "Put the code in" field have a choose-folder button as well. For "Put the code in", a project (it has a package.json, a `.git`, or an index.html for a plain HTML site, which also switches the framework to plain HTML), a folder inside a project (say `src/pages`, which follows that project's framework) or an empty folder is used as is; any other folder with files in it (say `~/Projects`) gets a new `<design>-app` inside, and a folder inside the design itself moves it alongside instead. A note under the field says when it changed. When no front-end framework is recognized (a backend, a monorepo root, a repo in another language), the handoff notes tell the model to look at the structure first and pick the right subfolder rather than scaffold in place. If the previewed page has its own upload area, a file dropped there still goes to the page.
26. **Gallery, My designs and Inspiration.** Three tabs in the middle of the home title bar (or type `/design-library` in the DSH input):
    - **Gallery:** templates (web, app, mini program, poster…), design systems and style cards that others shared, with search and filters by type and style. Open one to see each screen large; app, mini program, tablet, email and web designs also have a Live view, running under the hard rules described below. "Start from this" copies the whole set into the current session's folder and opens it on the canvas for the model to keep editing. The copy is yours and isn't affected if the gallery later removes the original; CC BY designs come with an `ATTRIBUTION.md`. "Add to design systems" installs a design system into your brand design systems; style cards go into Inspiration with Favorite. ☆ Favorite keeps a design in Inspiration. The catalog is cached locally, so you can still browse the last one offline.
    - **My designs:** every design you've made across sessions, recorded automatically. Search at the top; click a card to open it, and its ⋯ menu has Show in folder, Export design package, Submit to gallery, Pin and Remove from list; relocate it if the folder moved. A Designs / Frames switch shows your frame library: click a frame's thumbnail to start a design in it, and its ⋯ menu can Rename, Show in folder or Delete it (deleted frames go to the library's `.trash` and are cleared after 30 days). If the gallery template it came from was taken down, the card says so (your copy keeps working).
    - **Inspiration:** saved reference images (Use as reference), URLs, style cards (Save as my style stores the current design's look) and gallery favorites (taken-down ones are marked).
    Drop a design zip someone sent you onto the sidebar to start from it too.
27. **Submit to gallery.** Share › Submit to gallery (three steps), or Submit to gallery in a My designs card's ⋯ menu. Fill in a name and a one-line description, pick a license (CC0: anyone can use it; CC BY: they must credit you), tick four confirmations (you made it, the brand is made up, no real personal data, you agree to publish), then "Check and submit". The plugin checks the gallery rules first (real personal data is a hard stop), then opens every screen offline in the hidden browser: problems the review bot would reject (content under the system bar, broken images, links to missing pages) are caught here, and **Ask the model** hands them over in one click. A passing design becomes a zip in Downloads; then click "Submit". The first time you connect GitHub (the plugin shows a code, you enter it on github.com and approve); after that the plugin puts the zip in your own GitHub repository (forking the gallery the first time) and opens the submission issue, with no dragging files or ticking boxes again. Connecting only asks for access to your public repositories, the token stays on this computer, and "Disconnect" removes it. Rather not connect? "Use the web form" opens the submission page to drop the zip in. The bot replies on that issue within minutes, and the design is listed once reviewed. On My designs the card shows "Shared · not listed yet · Check progress", then "Listed · view in gallery". Submitting needs a GitHub account.
28. **Diagrams.** Roadmaps & diagrams sits right on the home page type row; pick it and a second row offers Technical roadmap (grant proposal), Research framework, Architecture, Mind map and Product roadmap, each switching the example and added to your message. You can also just ask for a mind map, a technical route chart, a product roadmap or a system architecture diagram and the model builds a `diagram`: mind maps (a central topic with branches on both sides, colored first-level branches fading level by level), technical route charts (the kind in grant proposals and theses: stage names on the left, rows of boxes in the middle with arrows drawn between stages and rows, automatic fan-out and fan-in when a row has several boxes, and optional outcomes per stage on the right), product roadmaps (a quarter or month timeline with lanes, bars, milestones and a "today" line; bars that do not fit drop to the next row) and architecture diagrams (layers top to bottom, optional groups inside a layer, and side columns for cross-cutting things like monitoring and security). The bundled `diagram.css` does all the positioning and lines, so the model only writes structure and nothing re-routes wrong when text changes or nodes are added. Colors come from the design tokens, with branch colors derived from the primary color, and dark mode works. The default size is 1600×1000; a tall proposal figure can use `diagram 1400x1800`, and the size grows when the diagram is larger. The design check adds five diagram rules: larger than the page size, nodes not written the expected way, too many items in one column or row, bars running past the timeline, and too much text in a node. The plain export is a 2× PNG that stays sharp in Word and PowerPoint, and PDF works too.. **DSH plugins.** Pick the "DSH plugin" type and every screen comes inside the DSH desktop frame, measured from DSH 0.2.2 in light and dark. After you edit a design by hand in the sidebar (adjust style, edit text, tweaks, restoring a version), the model gets a note before its next step: what changed, re-read the files, don't undo it. `preview_page` takes `target` (a file path, port or URL), `kind` (web / app / miniprogram / desktop / tablet / poster / slides / email / diagram), and optionally `size` (such as `1080x1920`) and `screens` (dev-server routes to show side by side). `check_design` takes `screens` (which ones to measure), `sizes` (such as `["375x667","430x932"]`), `dark` and `images` (`false` for no screenshots). `look_design` takes `screens`, `size`, `at` (top / bottom / full), `selector` (just this element) and `dark`. `extract_design_system` takes `sources` (1–5 URLs, project folders or HTML files), `name` and `default`. `handoff_design` takes `framework` (same / react / vue / next / html / uniapp / weapp), `dest` and `screens`. `compare_design` takes `url` (the actual page: a local address or port), `screen`, `size`, `at` (top / bottom) and `dark`.

## Design mode and switches

New sessions get a **Design** mode (shown as 设计模式) in the mode menu: all of Standard mode's tools plus the design skill and sidebar previews, with a design-focused persona. Pick it for design work; Standard, Creator and other modes keep these features too.

The plugin is split into parts, each with its own switch under DSH Plugins → Design Studio. Changes apply right away, no restart:

| Part | What it does | Default |
| --- | --- | --- |
| Design Studio | The sidebar and preview servers (turning it off means not using the plugin) | On |
| Open previews automatically | While designing, a written HTML file or a started dev server opens in the sidebar; off, the sidebar only offers a "Preview …" button | On |
| Preview and check tools (other modes) | Standard, Creator and other modes can use `preview_page`, `check_design`, `look_design`, `extract_design_system`, `handoff_design` and `compare_design` | On |
| Design skill (other modes) | Standard, Creator and other modes can load the `ui-design` skill | On |
| Design mode | The Design entry in the mode menu | On |
| Design library offline | The design library makes no network requests: no gallery catalog, no downloads. A catalog already cached still shows | Off |
| Requirement notes (experimental) | The model also writes `annotations.json` with the rules, states and edge cases the UI does not show. The Check panel in the sidebar gains a Notes tab: numbered markers on the page, cards on the right, each locating the other. Handoff notes include them. Designs take a little longer | Off |

To design only in Design mode and keep other modes clean, turn off the two "(other modes)" switches. Design mode carries its own tool and skill and ignores them.

## Security

Each preview gets its own random `127.0.0.1` port, which is a different origin from DSH.

- **Only the previewed folder is served.** Requests that resolve outside it are refused. That covers `../`, encoded `../` and symlinks pointing outside.
- **DNS rebinding is blocked.** The Host header must be a local name plus this port.
- **Sidebar messages are checked.** The page talks only to DSH's own origins (`dsh-app://app` on desktop, plus DSH's web address). Outgoing messages name that origin, and incoming ones must come from the parent window with a matching origin. Another site that embeds the preview gets nothing and can't drive it. If you open DSH's web UI through a reverse proxy or a domain, that address must be listed in DSH's `trustedHosts` (`dsh-client-connection` config); otherwise picking, text edit and export won't work there.
- **The API requires a DSH login.** `/dsh-design-studio/api/*` checks it through DSH's `connection` service. Older DSH builds without that service accept only same-origin local requests.
- **Phone preview is opt-in and locked down.** It listens only on this computer's LAN address (not 0.0.0.0) and checks the Host header. The link carries a random 128-bit token. On first open the phone trades it for an HttpOnly cookie scoped to that port, and the token leaves the address bar. Requests without it get 403. Stopping, or 30 minutes idle, closes the port, and the next start uses a new token. Anyone on the same Wi-Fi who gets the link can view it, so don't post it in a group chat.
- **The gallery is signed and pinned.** The catalog is a signed npm package (`dsh-design-gallery`) checked against ed25519 public keys pinned in the plugin; a bad signature, or a serial lower than the last one seen (a rollback), is rejected. Design files live in a second package (`dsh-design-gallery-packs`); every file is checked against the catalog's sha256, with size caps and path checks on unpacking. Only the npmmirror, Tencent Cloud and Huawei Cloud npm mirrors and registry.npmjs.org are contacted (raced, first answer wins), and redirects are followed only to those hosts. The takedown list is remembered locally, so a catalog that drops it can't bring a design back. Turning on "Design library offline" stops all of it.
- **Designs from others run under hard rules.** Gallery designs and dropped-in zips, while unmodified, are previewed with a strict CSP: only the plugin's own two scripts run, nothing loads from the network (styles, images and fonts come only from the local preview address), forms can't submit and nothing can be framed. The first gallery version doesn't accept scripts or font files anyway. Once you edit it, it previews as your own design.
- **Sharing leaks nothing personal.** The zip carries no local paths or source records, and images are stripped of EXIF/GPS. The share token stays in your own `design.json`; the zip and the catalog carry only its hash, used to recognize "listed".
- **Dev-server headers are relaxed only on the preview port.** When proxying a dev server, `X-Frame-Options` and CSP are removed there. The dev server itself is untouched.
